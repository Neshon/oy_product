# Библиотека компонентов — Django 6.1 + PostgreSQL 18

Веб-интерфейс и админка поверх **существующей** базы радиоэлектронных компонентов.
Django ничего не создаёт и не переносит в этих таблицах: все модели помечены
`managed = False` и просто читают и пишут данные в исходную схему.

## Что внутри

| Адрес | Что там |
|---|---|
| `/` | состав библиотеки: сколько записей в каждой группе |
| `/<группа>/` | таблица с поиском, фильтрами, сортировкой, пагинацией, выгрузкой CSV |
| `/<группа>/new/` | создание компонента |
| `/<группа>/<id>/` | карточка со всеми параметрами и списком аналогов |
| `/<группа>/<id>/edit/`, `/delete/` | правка и удаление |
| `/search/?q=` | поиск по всем группам, платам и их составам |
| `/boards/` | платы: список, состав, импорт BOM, выгрузка в Excel и CSV |
| `/servers/` | серверы и их состав: позиции, разузлование, «где применяется», импорт System BOM |
| `/duplicates/` | поиск дублей в библиотеке |
| `/admin/` | стандартная админка Django: рабочие таблицы и таблицы замен |
| `/healthz/` | проверка живости для Docker и обратного прокси |

Группы: CAPACITOR, CLOCK, CONNECTOR, DIODE, FUSE, IC, INDICATOR, INDUCTOR,
MECHANICAL, PCB, POWER_IC, RESISTOR, SWITCH, TRANSISTOR.
Таблицы замен `z_*` редактируются наравне с рабочими и помечены в интерфейсе
меткой «замена». В карточке любого компонента выводится блок «аналоги по OY ID»:
туда попадают все записи с тем же **OY ID** — и из основной таблицы, и из парной
`z_`-таблице, кроме самой открытой записи. Строки из таблицы замен помечены
чипом «замена». Если OY ID не заполнен, подобрать аналоги не по чему, и карточка
прямо об этом говорит.

Представление `Parts` в проект не входит: это объект уровня PostgreSQL,
с которым работает другой софт, и Django его не читает и не трогает.

### Роли

Кто что может:

| Роль | Компоненты | Платы и BOM | Дубли |
|---|---|---|---|
| Схемотехники | просмотр | просмотр, добавление, правка, удаление | — |
| Топологи | просмотр | просмотр | — |
| Библиотекари | просмотр, добавление, правка, удаление | просмотр | — |
| Администратор (суперпользователь) | всё | всё | доступ |

Роли — обычные группы Django. Создать их и раздать:

```bash
python manage.py init_roles
python manage.py init_roles --assign ivanov=Библиотекари --assign petrov=Схемотехники
python manage.py init_roles --list
```

Назначать роли можно и в админке: «Пользователи» → группы.

Вошедшему доступен просмотр всего: списки, карточки, платы, поиск.
Ограничены изменения и отчёт по дублям. Кнопки, которые пользователю
недоступны, не рисуются, а прямой заход по адресу возвращает назад с
объяснением — проверка стоит и в представлениях, не только в шаблонах.

Пользователь без роли видит библиотеку, но ничего не меняет: это и есть
режим «только чтение», и отдельная роль для него не нужна.

Ссылка «админка» в шапке видна только тем, у кого стоит «Статус персонала»
(`is_staff`), — то есть тем, кого админка вообще пустит. Проверяется именно
`is_staff`, а не суперпользователь: в админку ходят и за конструктором
выпадающих списков, и это работа библиотекаря. Права это не выдаёт — доступ
по-прежнему проверяет сама админка, скрывается только ссылка, которая иначе
привела бы к «у вас нет доступа».

Вход — по адресу `/accounts/login/`, форма своя. Админскую (`/admin/login/`)
использовать нельзя: `AdminAuthenticationForm` отказывает всем, у кого не
стоит «Статус персонала», а роли здесь — обычные группы Django, и `is_staff`
у схемотехника с топологом нет и быть не должно. Пока вход вёл в админку,
войти мог только персонал.

Сайт целиком закрыт: без входа не открывается ни одна страница. За это
отвечает штатная `django.contrib.auth.middleware.LoginRequiredMiddleware` —
проверка стоит посередине, а не декораторами на представлениях, потому что
декоратор легко забыть на новом представлении, и страница молча окажется
открытой. Здесь наоборот: закрыто всё, а открытое помечено
`login_not_required`, и все пометки собраны в одном месте — в таблице
маршрутов `config/urls.py`. Их три, и каждое по необходимости: форма входа,
выход и `/healthz/` для Docker.

Закрытость закреплена тестами (`ClosedSiteTests`, `LoginPageTests` в
`components/tests.py`): они проверяют, что неавторизованного разворачивают
на вход вместе со строкой запроса, что помечено ровно три адреса и что
`LOGIN_URL` не уехал обратно в админку.

Права раздаёт членство в группе, а не стандартный механизм разрешений
Django: таблицы компонентов неуправляемые, и права на них мало что значат.
Все проверки собраны в `components/permissions.py`.

## Быстрый старт

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env                # укажите параметры своей базы
python manage.py check_schema       # сверяет модели с реальными колонками
python manage.py migrate            # только служебные таблицы Django
python manage.py createsuperuser
python manage.py runserver
```

Интерфейс — <http://127.0.0.1:8000/>, вход — <http://127.0.0.1:8000/accounts/login/>.
Подробности в [установке и запуске](docs/install.md).

## Разработка

```bash
ruff check . && ruff format --check .   # линтер и форматирование
python manage.py check --deploy         # небезопасные настройки
python manage.py test                   # тесты
```

Настройки линтера — в `pyproject.toml`. Прямые зависимости перечислены в
`requirements.in`, а `requirements.txt` собирается из него:

```bash
uv pip compile requirements.in -o requirements.txt
```
