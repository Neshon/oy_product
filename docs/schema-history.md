# Переезды схемы (выполнено)

Разовые операции над базой, которые уже проведены. В рабочих инструкциях
им не место — они сбивают с толку того, кто разворачивает проект сегодня, —
но выбрасывать их нельзя: по ним видно, почему база и схемы называются
так, как называются, и что делать, если где-то остался стенд со старой
схемой.

Все скрипты идемпотентны: повторный запуск скажет, что делать нечего.

### Переименование базы и схем

Если база и схемы ещё называются по-старому (`postgres`, `public`, `app`),
переименовать их можно двумя скриптами. Оба идемпотентны: повторный запуск
скажет, что делать нечего.

```bash
# 1. остановите приложение и снимите копию
pg_dump -Fc -d postgres -f before_rename.dump

# 2. схема Django: app -> oy_system (компоненты остаются в public)
psql -d postgres -f sql/rename_schemas.sql

# 3. база: postgres -> oy_system_db (не из неё самой — отсюда template1)
psql -d template1 -f sql/rename_database.sql

# 4. в .env
#    POSTGRES_DB=oy_system_db
#    POSTGRES_SCHEMA=oy_system,public

# 5. проверка
python manage.py check_schema
```

Переименование схемы не трогает то, что внутри: таблицы, индексы,
ограничения, права и представление `Parts` ссылаются друг на друга по
внутренним идентификаторам, а не по имени схемы, и переезжают вместе с ней.

Два места, где переименование задевает не только нас:

* **Сторонний софт, который ходит в таблицы компонентов.** Если он не
  указывает схему явно, то полагается на `public` в `search_path` по
  умолчанию. Таблицы компонентов там и лежат, так что переименование схемы
  Django его не задевает — трогать сторонние подключения не нужно.
* **Имя `postgres` у базы.** Это служебная база кластера: к ней по умолчанию
  подключаются `psql` без `-d`, `pg_dumpall`, pgAdmin, мониторинг. Поэтому
  `sql/rename_database.sql` после переименования создаёт новую пустую
  `postgres` — ровно для них. Если данные лежат не в служебной базе, а в
  своей, передайте её имя: `-v old_name=<база>`, и пустая `postgres`
  создаваться не будет.

### Если компоненты уже переехали в oy_component_lib

Какое-то время таблицы компонентов держали в отдельной схеме
`oy_component_lib`. От этого отказались: всё, что ходит в них без явного
указания схемы — сторонний софт, представление `Parts`, ручные запросы, —
полагается на `public` в пути поиска по умолчанию, и каждому такому
подключению приходилось прописывать путь отдельно.

Вернуть библиотеку на место:

```bash
# 1. остановите приложение и снимите копию
pg_dump -Fc -d oy_system_db -f before_public.dump

# 2. oy_component_lib -> public
psql -d oy_system_db -f sql/use_public_schema.sql

# 3. в .env: POSTGRES_SCHEMA=oy_system,public
# 4. проверка
python manage.py check_schema
```

Скрипт идемпотентный. Занятое имя переименованию мешает, поэтому пустая
`public` (её заводит сам PostgreSQL) удаляется — но только пустая: если в
ней что-то лежит, скрипт останавливается и ничего не меняет.

Схема Django остаётся `oy_system` и в `public` не возвращается: смешивать её
служебные таблицы с библиотекой компонентов незачем, разделение как раз для
этого и делалось.

После переезда снимите постоянный путь поиска, если выдавали его ролям
стороннего софта, — он ссылается на несуществующую схему:
`ALTER ROLE <роль> RESET search_path;`

Схему `public` скрипт по умолчанию обратно не создаёт: приложению она не
нужна. Если у вас есть расширения или инструменты, которые её ждут,
раскомментируйте `CREATE SCHEMA IF NOT EXISTS public` в конце
`sql/rename_schemas.sql`.

### Переход со старой схемы

```bash
pg_dump -Fc -d oy_system_db -f before_tracker_url.dump
psql -d oy_system_db -f sql/add_tracker_url.sql        # колонка в 27 таблиц
psql -d oy_system_db -f sql/shrink_tracker_url.sql     # только если колонку
                                                       # создали varchar(1024)
psql -d oy_system_db -f sql/move_component_links.sql   # перенос накопленного
python manage.py migrate                               # удаляет oy_component_link
python manage.py check_schema
```

Порядок важен: миграция удаляет таблицу вместе с данными, и после неё
переносить будет нечего.

Оба скрипта работают по явному списку из 27 имён таблиц — тому же, что в
`components/models.py`. Если таблицы из списка в схеме нет, скрипт скажет об
этом и пойдёт дальше, а в конце предупредит, сколько не нашлось: молча
пропустить таблицу он не может. Если у компонента было несколько ссылок, в колонку
попадёт самая ранняя — скрипт переноса перечислит такие случаи в NOTICE до
того, как что-то изменит.

Импортировать можно двумя способами — логика у них общая, результат
одинаковый.

**Через браузер:** «Импорт ссылок» в боковом меню (доступно библиотекарям
и администратору). Галочка «Только проверить» стоит по умолчанию: сначала
страница показывает, что нашлось, а что нет, и лишь потом, если снять
галочку и выбрать файл ещё раз, ссылки записываются. Между показом и
записью на сервере ничего не хранится, поэтому увиденное посчитано ровно
по тому файлу, который отправляют.

Строки, которые уже завели раньше, в списках не показываются — ни в
найденных, ни в ненайденных: при повторной загрузке того же файла нужно
видеть, что осталось сделать, а не тот же длинный список. Их число видно
в сводке. Строка считается заведённой, когда ссылка стоит у всех найденных
записей; если артикул есть и в основной таблице, и в заменах, а заполнена
только одна, строка остаётся в списке.

Отчёт об импорте читают целиком, сверху вниз, поэтому таблицы на этой
странице растут по содержимому и своей прокрутки не имеют
(`.table-wrap--flow`), а страница прокручивается как обычная. Раньше они
были такими же окошками с прокруткой, как списки компонентов, и колесо мыши
над ними страницу не листало — выглядело это как зависание.

Блоки отчёта разделены контейнером `.stack`: отступ задан на нём, а не на
самой панели. Панели встречаются и внутри сеток со своим `gap` — в карточке
компонента, например, — и собственный `margin` у панели давал бы там двойной
зазор.

Главный результат — таблица **«компонент не найден»**: по ней видно,
каких компонентов в библиотеке ещё нет или где артикул записан иначе.
Отдельно перечислены задачи, попавшие сразу в несколько записей.

Для ненайденных подбирается **предположение** — похожий артикул со
ссылкой на карточку. Чаще всего это та же деталь, записанная иначе:

* `2N7002KTB_R1` в задаче против `2N7002KTB` в библиотеке — лишний
  суффикс катушки;
* `MMBT3904 7 F` против `MMBT3904-7-F` — другие разделители;
* `LM5066IPMHE` против `LM5066IPMHE/NOPB` — в библиотеке артикул длиннее;
* опечатка в конце — ловится нестрогим сравнением.

Сами ссылки по таким строкам не создаются автоматически: решение за
человеком. Рядом с каждым предположением есть кнопка **«Добавить»** — она
заводит ссылку именно на этот компонент, не уходя со страницы, так что
можно подтвердить несколько подряд, не теряя результаты импорта. Такие
ссылки помечаются источником «подтверждено вручную», чтобы позже было
видно, что их поставили руками, а не точным совпадением. Порядок
правил — по убыванию доверия, и первым показывается самое правдоподобное.
Два верхних правила ищутся по словарю, а дорогое нестрогое сравнение
считается только когда словарь ничего не дал и ограничено сверху: без
этого строка с распространённым началом артикула (типовые резисторы)
обрабатывалась бы полсекунды вместо миллисекунд.

**Через командную строку** (колонки «Ключ» и «Задача»):

```bash
python manage.py import_links links.csv --dry-run          # посмотреть
python manage.py import_links links.csv
python manage.py import_links links.csv --unmatched нет.csv
```

Название задачи (`Создание транзистора MMBT3904-7-F`) по шаблону не
разбирается: артикул бывает из нескольких слов, со скобками, а иногда
приклеен к слову без пробела. Вместо этого из названия берутся все
возможные куски и сверяются с артикулами библиотеки — побеждает самый
длинный, который в ней нашёлся. Источник истины здесь база, а не догадка
о формате строки. Проверяется Vendor PN, затем GBT PN.

Повторный запуск того же файла ничего не меняет: где стоит тот же адрес,
запись не трогается. Где стоял другой — он будет заменён, и число таких
замен команда выводит отдельной строкой.

Ссылка видна в карточке компонента как обычный параметр и правится в форме.
Убирать «сироты» больше не нужно: ссылка лежит в самой записи и удаляется
вместе с ней.

## «Применяется на платах» в карточке компонента

Показывается по одной строке на плату, сколько бы позиций компонент на ней
ни занимал. Раньше строка состава равнялась строке таблицы, и одна плата
с тремя позициями выглядела как три платы.

В строке собрано: обозначения всех позиций (объединённые, без повторов),
число позиций и суммарное количество. Если QTY не заполнен ни в одной
позиции, количество остаётся пустым, а не превращается в ноль.

Ограничение `USAGE_LIMIT` считается по строкам состава **до** группировки:
при очень широком применении компонента список плат может оказаться
неполным — это защита от чтения половины базы ради одной карточки.

## Переименование приложения: products -> servers

Раздел составов назывался `products`, стал `servers`: он ведёт серверы, их
конфигурации и то, что в них входит, и название раздела теперь совпадает с
тем, что в нём ищут.

Переименование пакета в коде базу не трогает: Django выводит имена таблиц
из метки приложения, поэтому в базе остались `products_item`,
`products_bomline` и строки `app = 'products'` в `django_migrations`. Если
запустить новый код на такой базе, `migrate` решит, что приложение
`servers` не мигрировано ни разу, и попробует создать таблицы заново —
поверх данных.

Порядок такой: сначала SQL, потом новый код.

```bash
# 1. остановите приложение и снимите копию
pg_dump -Fc -d oy_system_db -f before_rename_app.dump

# 2. таблицы, последовательности, журнал миграций и типы объектов
psql -d oy_system_db -f sql/rename_products_app.sql

# 3. запустите приложение — migrate накатит только то, чего ещё нет
```

Скрипт идемпотентный: то, что уже переименовано, пропускается.

Что переименование **не** требует чинить отдельно:

- **представление `bom_edge`** — PostgreSQL хранит ссылки на таблицы по
  внутренним идентификаторам, а не по именам, и переписывает определение
  представления само;
- **права и группы** — `auth_permission` ссылается на `django_content_type`
  по `id`, поэтому смена метки приложения роли не задевает;
- **имена ограничений и индексов** — остаются старыми
  (`products_bomline_parent_id_...`). По имени к ним никто не обращается,
  и переименовывать их значило бы усложнить скрипт ради косметики.

Адрес раздела тоже сменился: `/products/` → `/servers/`. Старые закладки
и ссылки из Confluence вернут 404 — редиректа нет намеренно, чтобы в
журнале было видно, кто ещё ходит по старому адресу.

## Приведение имён колонок к единому виду

В исходной схеме четыре колонки (`Dimensions`, `Height`, `Temperature min`,
`Temperature max`) были названы неодинаково от таблицы к таблице —
где-то с двойным пробелом, где-то с одним, где-то без пробела перед `°C`.
Остальные однотипные колонки везде оформлены как «Название, единица», и
к этому стилю приведены и эти четыре:

```bash
psql -d oy_system_db -f sql/rename_double_space_columns.sql
```

Скрипт идемпотентный — переименовывает то, что ещё не переименовано, и
не трогает уже приведённые таблицы. **После него `components/models.py`
уже обновлён** под новые имена (`db_column` и `verbose_name`) — отдельно
ничего править не нужно, порядок такой: сначала SQL, потом эта версия
кода. Пока не выполнили SQL — приложение будет падать с «column does not
exist» на этих полях, если запустить уже обновлённый код на старой схеме.
