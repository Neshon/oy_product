# Серверы и их состав

Раздел `servers` отвечает на два вопроса: из чего собран сервер и где
применяется деталь.

Назван он по верхнему уровню, но заведено в нём всё, из чего сервер
собирают: узлы, платы, кабели, корпуса, механика, материалы. Отдельной
таблицы под сервер нет намеренно — вложенность в производстве меняется, и
то, что сегодня плата, завтра оказывается узлом с собственным составом.
Конфигурация сервера — это отдельная позиция со своим OY P/N и своим
составом: так две конфигурации одной машины не путаются между собой и
каждая честно показывает, что в неё входит.

### Как устроено

Позиция (`Item`) — это сервер, узел, плата, кабель, корпус или материал.
Вложенность живёт не в позиции, а в строках состава (`BomLine`): «в позицию
A входит позиция B в количестве 2». Поэтому одна и та же плата стоит в трёх
серверах, оставаясь одной записью; при дереве её пришлось бы завести
трижды, и дальше расходились бы правки.

Получается граф, а не дерево. Единственное жёсткое ограничение — узел не
должен попасть внутрь самого себя через любую глубину: иначе разузлование
однажды уйдёт в бесконечный цикл. Проверка стоит в `BomLine.clean()`, а
обход всё равно ограничен глубиной — данные приходят и мимо приложения.

Ревизий у позиций нет: состав живёт прямо на позиции. Исключение — платы,
у них ревизии уже работают (импорт BOM, сравнение, переключение текущей).
Позиция-плата своего состава не хранит: её состав — строки текущей ревизии.
Обе стороны сведены представлением `bom_edge` (миграция `servers/0002`), и
обход об этом знать не обязан.

Строка состава указывает либо на другую позицию, либо на номер с описанием —
для того, чему карточки ещё нет. Количество дробное и с единицей измерения:
кабель меряют метрами, ленту — миллиметрами, целого числа штук не хватает.

Опознавательный номер — `OY P/N`. У механики из System BOM своего номера нет
вовсе, только номер поставщика, поэтому есть и `GCT P/N`: поиск идёт сначала
по своему номеру, потом по нему.

### Разузлование и применяемость

Обе задачи — один рекурсивный запрос по `bom_edge`, в разные стороны
(`servers/tree.py`). Вниз — с перемножением количеств: две платы по три
конденсатора дают шесть. Вверх — «где применяется»: выбрали конденсатор,
видите платы, а через них серверы.

Сводка (`tree.summary`) складывает только покупные позиции — то, у чего
своего состава нет. Иначе плата попала бы в неё и сама, и своими
компонентами, а итог получился бы вдвое.

### Импорт состава

```bash
python manage.py import_system_bom HN203I-1MPF-02.xlsx --dry-run
python manage.py import_system_bom HN203I-1MPF-02.xlsx
```

Файл читается с листа «System BOM»: партномер изделия в первой строке,
разделы (Boards, Cables, Mechanics, Other) отбиты строками из подчёркиваний,
колонка `M/S` отличает основную строку от замены. То же самое доступно на
сайте — «Импортировать System BOM».

Позиции, которых ещё нет, заводятся заготовками со статусом «в разработке»:
состав не должен ждать, пока кто-то заполнит карточку.

**Повторный импорт заменяет только свои строки.** Строки, заведённые руками,
остаются на месте — иначе первая же повторная заливка стёрла бы ручную
работу. Отличаются они по полю `source`.

Что импорт сообщает отдельно: строки без пометки `M/S` (принимаются за
основные, но молча терять их нельзя) и количество, которое не разобралось в
число, — в файле встречается запись вида «90 мм», и исходное значение
уходит в примечание строки.

### Перенос из Confluence

Страницы изделий разбираются отдельным скриптом, а загружаются командой:

```bash
python manage.py import_cards ./pages                # сначала платы
python tools/confluence_parse.py ./confluence -o confluence.json
python manage.py import_confluence confluence.json   # потом изделия
```

Разбор отделён от записи намеренно: разметка страниц разъезжается от
шаблона к шаблону, и править приходится именно разбор. Заодно JSON можно
посмотреть глазами до того, как что-то попадёт в таблицы.

Карточки печатных узлов отдельными позициями не становятся: они ложатся
полями внутрь карточки своей платы. Ревизии ведёт раздел плат, дублировать
их позициями значило бы завести 57 записей вместо 12. Сами эти карточки
`import_confluence` тоже не пишет — их грузит `import_cards` прямо из
markdown, одним разборщиком, без промежуточного JSON. Отсюда и порядок
команд выше: позиция-двойник платы ищет её в реестре по номеру, и если
платы ещё нет, заведётся обычная позиция без связи. Чинится `sync_boards`.

### Позиции для плат

На каждую плату заводится позиция-двойник — иначе строку «в сервер входит
материнская плата» не с чем связать. Синхронизация односторонняя, от платы
к позиции, и запускается сама при импорте BOM и правке платы. Для плат,
заведённых мимо приложения:

```bash
python manage.py sync_boards
```
